# Gradual build

A program decided in stages, each stage's work kept only as long as something
can reach it. The load fixes what the declarations decide and parks what they
leave open; a settlement settles what one binding of load content at one seam
decides, and every frame under that binding reads it; a frame decides what a
binding of run content leaves open in its own activation. A type a stage
builds lives in that stage's tier — the root for the load, the agent tier for
a settlement under the root, a region's branch or a scratch branch — and goes
with it. What it buys the language: a body typed as far as its first
binding allows, once, with no verdict re-derived per read; a long-running
program whose loops view modules and build types holds a bounded lattice; and
a body's types die with the call instead of with its host.

[The build module](../../src/build/README.md) owns the solver, its stores and
the keys, and [the scheduler](../../src/scheduler/README.md#the-build-arena) the
build arena its settlements and compositions live in;
[the type tiers design](../../design/type-tiers.md)
tells where a run-built type lives. The pieces sit in the
[type lattice](../../lattice/src/types/identity.md#storage-a-root-and-its-branches),
[the load's walk](../../src/build/README.md#the-one-walk),
[static types](../../src/dispatch/README.md#static-types),
[the program](../../src/program/README.md),
[the scheduler](../../src/scheduler/README.md) and
[knots](../../src/knot/README.md).

## Unplanned work

Known gaps with no item behind them yet — recorded so they are not rediscovered
as surprises, not scheduled.

- **A `FOR ALL` name past a header or a barrier.** A call of a body keyed on a
  `FOR ALL` name through a header or a barrier seeks no settlement: the frame solves
  the node's own group only after it retypes or crosses the arguments, and a
  barrier's crossing (`coerce::inward`) is a value operation the asker cannot
  run before the frame is born. Keying it needs that solution computed from
  types alone.
- **A site the load finds by searching its body.** A type path whose root is
  written in place (`:((ID b).Carrier)`) and a read of a name bound to a
  `FOR ALL` function find their part's statement by searching every statement
  of the body (`dispatch/walk.rs` `source`, `walk/paths.rs` `resolve_entry`),
  so a body of n such reads loads in O(n²). The base the one walk replaced
  searched alike. A site-to-statement index on the shape would answer both.
- **A member chain written through a leaf.** Each part of a written chain
  `p.a1.….an` through a leaf is its own tree holding its own chain, so the load
  lays n(n+1)/2 labels for it and hashes each of them again in the leaf's
  digest (`Tree::bound`). Two steps would make it linear:
  - A leaf carries its chain's running digest, so extending it hashes one
    label, and a chain's first tree read lays its labels once, each part a
    prefix of them, as `read_chain` shares a joined chain. Parts read inner
    first, as `holds_nothing_minted` reads an operand nothing received, still
    lay their own chains.
  - The shape lays each written member chain's labels together, so a leaf on a
    parameter borrows its chain from the shape and any other leaf joins its own
    chain to them once per root, whatever order the parts are read in.
