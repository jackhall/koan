# Performance

What a program pays, at the depth and length its data sets and per
operation. A value's carried type nests as deep as the value, a loop that
views a module over a chain walks the chain each hop, and a relation that
misses its verdict cache records its answer through a probe of every tier:
a cost that is a constant at the sizes a test writes is a wall or a slope at
the sizes a program reaches. The items here run every walk over the type
lattice on an explicit stack, keep what a loop would otherwise derive again
each hop, and lay what a program run interns at the size it reaches. What it
buys the language: a program as large or as deep as its data, at a cost that
grows with the data and no faster. A cost the load can decide away by
deciding more is [one build](../one-build/README.md)'s.

## Unplanned work

Known gaps with no item behind them yet — recorded so they are not rediscovered
as surprises, not scheduled.

- **Binding a knot's members walks the knot per member.**
  [`Knotted::of`](../../src/knot/tie.rs) resolves member `index` through
  `knot.members().nth(index)`, O(n) per call, so binding a component's k
  members is O(k²). The knot has no index→member door, since an edge is minted
  only by a `KnotPlan`.
- **A value's weight counts a knot once per reference.** A knot member weighs
  its whole knot ([weight](../../src/values/README.md#weight)), and a
  composite's weight is the sum of its cells', so a value holding two members
  of one knot weighs that knot twice, though a crossing copies it once. The
  verdict then leans toward pinning. A memoized weight cannot see sharing below
  it without a set of knots per composite.
- **A knot copied whole keeps a tagged payload's hidden fields.** A copy lays
  down only what a value's type names ([crossing](../../src/values/README.md#crossing)),
  but a knot seen at its own memo is re-tied cell for cell. A tagged data node's
  memo is its identity, and its payload may be wider than the representation:
  after `LET c = (Point {x = 1, y = 2, z = c})`, a copy of `c` still lays down
  `z`. No read sees it, since the door hides it, but it counts in the copy's
  weight, and so in the copy-or-pin verdict.
- **A site the load finds by searching its body.** A type path whose root is
  written in place (`:((ID b).Carrier)`) and a read of a name bound to a
  `FOR ALL` function find their part's statement by searching every statement
  of the body (`dispatch/walk.rs` `source`, `walk/paths.rs` `resolve_entry`),
  so a body of n such reads loads in O(n²). The base the one walk replaced
  searched alike. A site-to-statement index on the shape would answer both.
- **A member chain written through a leaf.** Each part of a written chain
  `p.a1.….an` through a leaf is its own tree holding its own chain, so the load
  lays n(n+1)/2 labels for it and hashes each of them again in the leaf's
  digest (`Tree::bound`). Two steps would make it linear:
  - A leaf carries its chain's running digest, so extending it hashes one
    label, and a chain's first tree read lays its labels once, each part a
    prefix of them, as `read_chain` shares a joined chain. Parts read inner
    first, as `holds_nothing_minted` reads an operand nothing received, still
    lay their own chains.
  - The shape lays each written member chain's labels together, so a leaf on a
    parameter borrows its chain from the shape and any other leaf joins its own
    chain to them once per root, whatever order the parts are read in.
